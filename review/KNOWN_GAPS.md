# 已知红灯与豁免清单（KNOWN GAPS）

> **性质**：这不是「永久豁免机制」，是「**已知、已判定不修、且有据可查**」的账本。
> 每条须 Master 明确批准才能登记；未登记的红灯一律视为真缺陷。
> **新产物无豁免**：清单只对列出的具体日期/对象生效，一律不做日期范围通配。

**最后更新**：2026-11-10
**批准人**：Master
**关联版本**：v10.5.0 门禁机制改造 8 项（其中 ② claims 契约、③ v2 复检件为本清单的成因）

## 一、A8 claims 契约（gate_check，Phase 3.8 shadow）

判定逻辑：`probe_claims()` 区分 `absent / null / not_list / empty / ok` 五态。
缺键、`null`、类型错、或「claims 为空但 `fact_check.key_facts` 有已核事实」均判 **fail**。只有真空账本判 skip。

### G-01｜2026-11-09｜claims 缺失，key_facts 有 8 条

- **状态**：维持 `A8 = fail`
- **为什么不补**：该日 `fact_check.key_facts` 是 L1 阶段的扁平键值对，共 8 条（`datetime` / `cause` / `area_sq_mi` / `people_affected` / `load_lost_mw` / `duration_hours` / `nyc_subway_trapped` / `aftermath`），**无来源字段、无核实状态**。机械转成 claims 等于把「事实草稿」包装成「已核对账本」。
- **决定性证据**：第 8 条为
  `aftermath = 1968年成立北美电力可靠性公司（NERC）`
  而当日 L2 学习已把它证伪并修正：1968 年成立的是 **National Electric Reliability Council（理事会）**，`Corporation` 是 2006 年才改的。**错的原始数据至今仍留在 key_facts 里**。把这条转成 claims 并「核实」，产出的将是错误的合规结论。
- **正确处置**：不补。此案例保留为「key_facts 不是核验账本」的反面教材，写进 SKILL。

### G-02｜2026-11-06｜claims 显式为 null

- **状态**：维持 `A8 = fail`
- **为什么不补**：该日产物 `claims` 字段显式为 `null`，而 claims 契约在 11-09 才落地。该日并未产出核验账本，事后补写即伪造当时的核对过程。
- **正确处置**：不补。

## 二、v2 复检件（sync_check ⑫）

判定逻辑：`v2_review_since = "2026-11-10"`，**只对 2026-11-10 及之后的 v2 产物**强制要求 `{date}_v2_review.json`。

### 不登记为豁免项（说明性条目）

10 月至 11 月初共 23 篇 v2，仅 2 篇有复检件（10-30、11-03），即 **21 篇缺件**。

- **这不是红灯**：⑫ 的设计就是不追溯历史，上述 21 篇本就不在检查范围，因此**无需豁免、也不应登记为豁免**。登记会造成「漏洞比实际更大」的错觉。
- **为什么不补**：v2 复检是当时的**独立审校过程记录**，事后补写的是文件，不是过程，等于伪造。
- **新产物**：自 2026-11-10 起，任何 v2 缺 `_v2_review.json` 一律报 `v2 缺复检件 N 篇`，无豁免。

## 三、登记规则

1. 新增条目前提：已确认**无法修复**（如上游数据本身错误、过程记录无法回溯），而非「修起来麻烦」。
2. 必须写明：对象（精确到日期/文件）、状态、不修理由、可验证证据。
3. 禁止写日期范围通配（如「11 月以前全部豁免」），必须逐条列举。
4. 修好一条就从本文件删除一条，不留「已修复」的僵尸条目。
5. 每次改动本文件后跑 `python scripts/sync_check.py` 确认 24/24 不受影响。
