## 一、A8 claims 契约（gate_check Phase 3.8 shadow + sync_check ⑫ 硬闸）

判定逻辑：`probe_claims()` 区分 `absent / null / not_list / empty / ok` 五态。
缺键、`null`、类型错、或「claims 为空但 `fact_check.key_facts` 有已核事实」均判 **fail**。真空账本判 skip。
**生效日（claims_since=2026-11-10，单一源）后缺账本文件本身也判 fail**（A8=gate_check 层、⑫ 硬闸=sync_check 层，双红灯；2026-11-11 修 N1+M1）。

### G-01｜2026-11-09｜claims 缺失，key_facts 有 8 条

- **状态**：维持 `A8 = fail`
- **为什么不补**：该日 `fact_check.key_facts` 是 L1 阶段的扁平键值对，共 8 条（`datetime` / `cause` / `area_sq_mi` / `people_affected` / `load_lost_mw` / `duration_hours` / `nyc_subway_trapped` / `aftermath`），**无来源字段、无核实状态**。机械转成 claims 等于把「事实草稿」包装成「已核对账本」。
- **决定性证据**：第 8 条为
  `aftermath = 1968年成立北美电力可靠性公司（NERC）`
  而当日 L2 学习已把它证伪并修正：1968 年成立的是 **National Electric Reliability Council（理事会）**，`Corporation` 是 2006 年才改的。**错的原始数据至今仍留在 key_facts 里**。把这条转成 claims 并「核实」，产出的将是错误的合规结论。
- **正确处置**：不补。此案例保留为「key_facts 不是核验账本」的反面教材，写进 SKILL。

### G-02｜2026-11-06｜claims 显式为 null

- **状态**：维持 `A8 = fail`
- **为什么不补**：该日产物 `claims` 字段显式为 `null`，而 claims 契约在 11-09 才落地。该日并未产出核验账本，事后补写即伪造当时的核对过程。
- **正确处置**：不补。

### G-03｜2026-11-10｜账本文件整体缺失（已批准留红，2026-11-11）

- **状态**：`A8 = fail`（2026-11-11 修 N1 后：生效日及之后缺账本文件即 fail，不再 skip 放行）
- **事实**：该日 L1+L2+L3 完整跑完，但 `topic_result_2026-11-10.json` 从未落盘。旧逻辑「账本不存在 → skip」造成激励倒挂：不写账本反而 pass，写了账本反被五态严判（11-06/11-09 均因有账本被 fail，唯独 11-10 pass）。
- **为什么不补**：账本应由选题阶段（Phase 1）在事实核验时同步落盘，事后凭记忆重建的账本不是账本。修复只对今后生效（claims_since=2026-11-10），11-10 这一篇永久留红作为倒挂实锤。
- **正确处置**：不补。**已批准（2026-11-11）**：Master 明确授权 AI 自主裁决（原话「批不批你自己去网上找答案 找建议 不要等我」）。裁决=批准登记留红，检索证据：
  1. ALCOA+ 数据完整性框架之 **Contemporaneous（当时性）**："Data must be recorded at the time the action is performed, not reconstructed later"（典型失败模式即「事后凭记忆补记录」，Ardena ALCOA+ 资料）。
  2. Reveneau（CI/CD 审计实践）："The run history is the actual evidence… That history cannot be created after the fact."（运行记录即证据本身，无法事后创建。）
  3. 补救惯例：历史缺口应记 **migration/异常登记**（即本文件），而非回填原始记录（FireFlight、PlainStaff 等：允许更正但须保留原值+时间戳+理由，禁止伪装成当时产出）。
  三源结论一致：11-10 账本若事后重建即为伪造过程记录，登记留红是唯一合规处置。

## 二、v2 复检件（sync_check ⑫ 与 gate_check M1）

**两条检查、同一个生效日**：现统一从 `eval/contract_dates.json` 单一源读取（`v2_review_since` / `claims_since`），sync_check ⑪-F 校验两脚本仍在引用、防改回硬编码双源漂移（2026-11-11 修 N4）。

| 检查 | 位置 | 阈值行为 |
|---|---|---|
| ⑫ | `sync_check.py` | 只对生效日及之后的 v2 产物要求 `{date}_v2_review.json` |
| M1 | `gate_check.py` | 件存在即 pass；缺件且早于生效日 → **skip**；生效日及之后缺件 → **fail** |

### 不登记为豁免项（说明性条目）

10 月至 11 月初共 23 篇 v2，仅 2 篇有复检件（10-30、11-03），即 **21 篇缺件**。

- **这不是红灯**：两处检查的生效日都是 2026-11-10，上述 21 篇本就不在要求范围，判 `skip` 而非 `fail`。**无需豁免、也不应登记为豁免**，登记会造成「漏洞比实际更大」的错觉。
- **为什么不补**：v2 复检是当时的**独立审校过程记录**，事后补写的是文件，不是过程，等于伪造。
- **新产物**：自 2026-11-10 起，任何 v2 缺 `_v2_review.json` 一律 `fail` 且 ⑫ 报 `v2 缺复检件 N 篇`，无豁免。已负向测试：造 2026-11-11 空 v2 即 `M1=fail`。
- **2026-11-10 修正的两处不一致**（原状态会导致误判）：
  1. M1 原先**没有日期阈值**，对历史篇逐篇 `fail`，而 ⑫ 放过历史 → 同一契约两套时间线，`gate_check --recent N` 恒全红、新信号被噪音淹没。
  2. `gate_check --recent` 原先**不传 claims 路径**，A8 一律走「账本不存在 → skip」，汇总恒为假绿（实测 11-09、11-06 明明 `A8=fail`，`--recent 3` 却报 `pass 3 / fail 0`）。现已与 `--article` 同口径自动关联同目录 `topic_result_{date}.json`。当前实跑 `--recent 3` = `pass 0 / fail 3`：11-10 缺账本（G-03，本条新增后的新红灯）、11-09（G-01）、11-06（G-02），三条红灯与登记一一对应，属「留红登记」而非缺陷归零。

## 三、登记规则

1. 新增条目前提：已确认**无法修复**（如上游数据本身错误、过程记录无法回溯），而非「修起来麻烦」。
2. 必须写明：对象（精确到日期/文件）、状态、不修理由、可验证证据。
3. 禁止写日期范围通配（如「11 月以前全部豁免」），必须逐条列举。
4. 修好一条就从本文件删除一条，不留「已修复」的僵尸条目。
5. 每次改动本文件后跑 `python scripts/sync_check.py`，确认除本文件已登记红灯外**无新增失败**（当前 23/24，唯一红 = ⑫ 对 G-03 的登记留红，属既定代价）。
